# Architecture

`master/app.py` creates the FastAPI application. The dashboard and placeholder pages are rendered by `master/pages.py`, using CSS and a small search script in `shared/ui/`.

Each tool has its own folder under `tools/`, a `README.md`, and a `tool.json` manifest. On startup, `master/registry.py` reads manifests from the immediate child folders. Adding a folder with a valid manifest adds a dashboard card and placeholder page without editing the master or another tool. The manifest interface consists of a unique lowercase hyphenated `slug`, a display `name`, and a one-sentence `purpose`. Its page is `/tools/{slug}`. A tool can implement that page by adding `tool.py` with `initialize(database_path)` and `register(app, database_path)` functions. The master loads that module before its placeholder route. All ten tools use this interface.

`shared/database/storage.py` owns SQLite connection setup and creates `campaigns`, `parties`, and `party_members` tables. The PC roster has stable member IDs and stores name, class, optional HP and Speed, and short notes. `shared/party_roster.py` exposes the roster API; Adventure Planner edits it while Combat Tracker reads it. It enables foreign keys for each connection. The database is initialized when the app starts and is stored locally in `data/pf2e.sqlite3`. Rules Quick Reference adds its own `rule_references` table in the same database and seeds ten read-only official examples. User notes and house rules are editable local records.

Skill & DC Helper keeps the official DC tables and degree logic in its own pure `calculator.py` module. Its single-page UI calls a local FastAPI calculation endpoint. It does not alter the Rules Quick Reference database or store check inputs.

Encounter Builder keeps GM Core XP tables and encounter calculations in its own pure `calculator.py`. Its `tool.py` adds `encounters` and `encounter_creatures` tables to the local SQLite database and exposes local calculate, template, and saved-encounter routes. The shared party table has no active party or level and size fields, so Encounter Builder stores its own party settings with each encounter. Its page uses local JavaScript for immediate updates.

Monster Library stores user-created monster data as version 1 JSON in its own `monsters` table. `model.py` validates GUI and JSON imports and derives completeness from actual fields; the label is not stored. Session Monster Collections use a join table and stable monster IDs. Encounter Builder may retain an optional monster ID for a creature group. A read-only `app.state.monster_lookup` interface lets Encounter Builder and Combat Tracker copy current library data without implementing a second monster model. Deleting a library monster leaves saved encounter groups usable as manual entries. Combat copies are independent snapshots with full initial HP.

Combat Tracker keeps turn progression, initiative, MAP, HP, and effect-label state changes in its pure `state.py`. Its `tool.py` stores independent combat snapshots in `combat_sessions` and applies each UI command in a SQLite transaction, so edits persist immediately. Phase 4 integration is read-only: it copies saved creature names and quantities into a new combat, with HP and initiative left unset. The original encounter record is never used as running combat state.

Combat Tracker can also copy shared PCs into a new or existing combat through `party_id`. Each copied PC carries its stable `party_member_id` and class; repeated imports add only missing PCs. Initiative remains unset. Combat HP is independent of the roster. The explicit `sync-party-hp` endpoint copies current and maximum HP back to existing roster members after GM confirmation; it never runs during ordinary combat edits. Deleting a roster member does not alter saved combats.

Conditions Tracker keeps concise verified rule definitions in `library.py` and pure condition calculations in `logic.py`. Its own SQLite tables hold standalone subjects and active condition sources. A combat-linked condition uses `(combat_id, combatant_id)` from Combat Tracker instead of creating another combatant. The Combat Tracker reads `/api/conditions/combat/{id}/summary` for compact labels and turn reminders, and writes through the Conditions API. Deleting a combat or combatant removes its associated conditions. Recovery checks are retained in the condition table after successful recovery, with inactive records omitted from current condition views. Existing manual effect notes remain in Combat Tracker as separate free text.

For round-duration conditions, Conditions Tracker registers `app.state.condition_round_tick(connection, combat_id, controller_id, event)` as a narrow write interface. Combat Tracker calls it in the same SQLite transaction as turn advancement for the outgoing end and incoming start events. Counters stop at zero and remain stored until the GM removes the condition.

Healing & Death Helper puts deterministic recovery, knockout, First Aid, and treatment calculations in `tools/07-healing-death/rules.py`. Its `storage.py` reads and writes Combat Tracker HP and Conditions Tracker's active Dying, Wounded, Doomed, and Unconscious rows by stable combatant ID. Only Hero Points, standalone HP, explicit game minutes, and treatment records are stored in Phase 7 tables. The Combat Tracker reads a Phase 7 start-of-turn recovery reminder through `/api/healing-death/combat/{id}/reminders`; both tools link to the same character. Treatment and emergency changes use one SQLite transaction so linked HP and conditions stay in sync.

Exploration Helper keeps verified activity summaries, travel calculations, and encounter reminder logic in `tools/08-exploration/rules.py`. Its session, member activity, and chronological log tables are separate from shared `parties` and Combat Tracker's combatants. Optional PC imports retain a stable combatant ID and read its current name from combat state. A linked exploration session uses the existing combat-scoped `healing_clocks` row; independent sessions use a new exploration scope in the same table. The Combat Tracker reads `/api/exploration/sessions/{id}/encounter` for an advisory checklist when opened from Exploration; it does not apply initiative bonuses or create combatants automatically.

Treasure & XP Helper keeps GM Core tables and progress calculations in `tools/09-treasure-xp/rules.py`. Its `reward_trackers` table has one optional foreign key to each shared `parties` row and holds that party's sole XP total. `treasure_rewards` stores editable plans and award status. Immutable `xp_transactions` record awards and reversals; `reward_events` record treasure corrections and level-up events. Encounter XP previews call Encounter Builder's existing deterministic calculator with saved encounter rows. Combat Tracker provides a link from ended combats to the reward page, with an optional saved encounter ID; it never writes rewards itself.

Adventure Planner stores adventures, ordered scenes, optional scene connections, NPCs, clues, items, sessions, and event notes in its own SQLite tables. Scene order is advisory; status changes are explicit. NPC, clue, and item associations use link tables so a single record can appear in several scenes. `adventure_scene_encounters` holds a stable saved Encounter Builder ID without a foreign key: a deleted encounter leaves the scene and link intact, and the planner reports the reference missing. Encounter summaries call Encounter Builder's calculator at read time; planner code does not own encounter XP rules or modify encounters. Campaign and party references point to shared records. Session recaps and Markdown export use deterministic `logic.py`; JSON import remaps local IDs within a transaction. UI changes persist through local API calls.

The application depends only on local Python packages and SQLite. It does not call any external service.
